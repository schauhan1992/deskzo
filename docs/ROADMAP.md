# Deskzo One — build history

> How the product was built, phase by phase, in the order it happened. It began as Wroffy's own CRM, grew into an ERP, and became Deskzo One, a multi-workspace SaaS, in September 2026: earlier entries keep the names used at the time.

> Scope note: this started as a CRM and is now explicitly headed toward a full customized ERP (per the user, 2026-09-10). Build every new capability as its own module registered in `src/lib/modules.ts` (nav group + nav items + optionally `core`) so it plugs into the sidebar and the Settings on/off toggle automatically — don't bolt features onto existing pages/nav by hand.

## Delivered (Phase 1 + 2 — Foundation & Lead pipeline)

- Next.js 15 app, Postgres via Docker Compose, Prisma schema.
- Auth.js credentials login, role-based `User` model (`ADMIN`, `PROFILE`, `CALLING`, `SALES`, `SUPPORT`, `MANAGEMENT`).
- `Company` (globally unique by normalized name), `Contact`, `Lead`, `Activity`, `Proposal` (structure only) models.
- Company CRUD (create with contacts, list with stage/search filters, detail view).
- Lead pipeline: create against a company, kanban-style board by status, status transitions (with required reason for Lost/Disqualified), activity timeline (calls/emails/notes/meetings), auto-flip of `Company.stage` to `CUSTOMER` on a `WON` lead.
- Raw data profiling: extended `Company` fields (category, company type, employee count, LinkedIn URL, GST/D-U-N-S numbers, country, tags), an edit page so profiling is progressive rather than one-shot, inline "add contact" on the company detail page, and bulk select + assign-to-calling-team-or-person on the companies list (`assignedTo`/`assignedBy`/`assignedAt` on `Company`).
- **Module system**: `SystemModule` table + a code-side `MODULE_REGISTRY` (`src/lib/modules.ts`) — an admin-only `/settings` page lists every module with a toggle. "Companies & Leads" is marked `core` (always on); "Items & Inventory" is the first real toggleable module. Disabling a module hides its nav link and every one of its pages/server actions checks `isModuleEnabled()` and refuses, not just the UI — verified live (toggled Items off, confirmed the page, nav, and server actions all blocked it, then re-enabled it).
- **Items & Inventory** (the first toggleable module): `Item` catalog covering `GOOD` / `SERVICE` / `SUBSCRIPTION` types in one table — SKU (unique), category, vendor, unit, billing cycle (subscriptions), cost/selling price, GST rate, active flag. Only `GOOD` items track stock; `trackInventory` is force-normalized server-side so a Service/Subscription can never end up with a stock ledger (form UI also resets the hidden field, but the server is authoritative — this exact bug was caught and fixed during testing). Inventory is a proper ledger (`StockMovement`: RECEIVED/SOLD/ADJUSTMENT/RETURNED/DAMAGED, signed quantity change) with a cached `stockQuantity` counter on `Item` kept in sync transactionally, opening stock on item creation, a reorder-level low-stock indicator, and a hard floor at zero (selling more than on-hand is rejected with a clear error — verified).
- **Sidebar shell**: replaced the top nav bar with a collapsible-on-mobile sidebar (`src/components/layout/sidebar.tsx`) that renders grouped nav sections straight from `MODULE_REGISTRY` (each module declares a `navGroup` + `navItems`) — a new module needs zero layout changes to appear in the sidebar. Icons are lucide-react components kept in the (client-importable, non-serialized) registry module rather than passed as Server Component props, since React component references can't cross that boundary. Settings is a fixed admin-only entry outside the module list. Verified desktop (grouped links, active-route highlighting) and mobile (hamburger → overlay drawer) live in-browser.
- **Lead ↔ Item requirements**: leads now capture which catalog products/services/subscriptions are needed (`LeadRequirement`: item + quantity + notes), pickable at lead creation and addable/removable afterward on the lead detail page, with a computed line total (unit price × qty) shown per line. This is the first cross-module link in the app — the "Products required" UI only renders when the Items module is enabled (`isModuleEnabled("items")`, checked both server-render-side and inside the `addLeadRequirement` action), and existing `LeadRequirement` rows are preserved (just hidden) if Items gets disabled later. Verified live: added/removed products on a real lead, and confirmed the section disappears/reappears correctly when toggling the Items module off/on.
- **Company search-and-create on the lead form**: the plain company `<select>` on "New lead" is now a type-ahead combobox (`src/components/leads/company-combobox.tsx`) filtering the already-loaded company list as you type, with a "+ Create new company" option when nothing matches. That opens a lightweight modal (`src/components/ui/dialog.tsx` + `quick-create-company-dialog.tsx`, name/industry/source/city/state only — full profiling still happens on the company page afterward) that creates the company inline and auto-selects it, no page navigation. Caught and fixed a real bug here during testing: the combobox's "sync displayed text to the selected company" logic was firing on every value change including the one *caused by the user typing* (which clears the selection), wiping out what they'd just typed — fixed by having the combobox mark its own value changes so the external-sync logic only fires for genuinely external updates (e.g. the modal handing back a new company id). Also swapped both dialog components' "reset state when a prop changes" effects for React's synchronous-render-adjustment pattern, since the newer eslint-plugin-react-hooks flags `setState` inside effect bodies as a real error, not a style nit.
- **Industry as a managed picklist**: `Company.industry` was free text; it's now a proper `Industry` table (id/name, unique) with `Company.industryId` as the FK, selected via a `<select>` everywhere it appears (new/edit company, the lead-form quick-create modal). Admins add and rename industries from a new "Industries" section on `/settings` (`createIndustry`/`updateIndustry`, admin-only like module toggles) — renaming propagates instantly to every company referencing it since it's a relation, not a copy. Migrated live data rather than dropping it: added `Industry` + a nullable `industryId` column first, ran a one-off backfill script that deduped the existing free-text values into `Industry` rows and pointed each company's `industryId` at the right one, *then* dropped the old text column in a second migration — verified the two pre-existing values ("Manufacturing", "Financial Services") survived with `prisma migrate status` showing no drift.
- **Items import/export**: "Import CSV" / "Export CSV" on the items list, plus a downloadable `public/items-import-template.csv` sample (one row each of a Good, a Subscription, and a Service, showing every column). Uses `papaparse` server-side for real CSV parsing (quoted fields, embedded commas) rather than a hand-rolled splitter, since this handles user data. Import is an upsert by SKU processed row-by-row (not one all-or-nothing transaction), so one bad row doesn't block the rest — the dialog reports created/updated counts plus a per-row error list. Deliberately asymmetric create vs. update: importing a *new* SKU can seed opening stock (creates a `RECEIVED` stock movement, same as the manual "New item" form); re-importing an *existing* SKU updates its details but never touches `stockQuantity` — the stock ledger stays the only way to move stock, so a bulk re-import can't silently corrupt it. Export sanitizes any cell starting with `=`, `+`, `-`, or `@` (prefixes a `'`) to guard against formula injection if the CSV is opened in Excel/Sheets. Verified live: imported the sample file against a catalog that already had 2 of its 3 SKUs — got "Created 1, updated 2" exactly as expected, and confirmed the existing Good's `stockQuantity` (104) was untouched even though the template's `openingStock` column said 20; then exported and confirmed the CSV reflected all three items correctly.

### Sales & Purchase documents, with GST and e-invoicing

  Six document types on one model (`TradeDocument` + `TradeDocumentLine`): **proposal → proforma invoice → tax invoice → credit note** on the sales side, **purchase order → vendor bill** on the purchase side. They share a party, dated lines, GST maths, numbering and totals, so splitting them into six near-identical models would have meant six copies of the tax engine; `docType` and `direction` say which one a row is.

  **The GST engine** (`src/lib/gst-engine.ts`) turns on one rule: a supply is CGST + SGST when the seller's state matches the place of supply, and a single IGST charge when it doesn't. That decision is made once in `resolveSupplyType` and every line follows it. Tax is computed per line and then summed — never on the invoice total — because rounding a mixed-rate invoice at the total gives a different (and wrong) answer to the sum of its lines. Round-off is tracked separately so the printed invoice reconciles. Also here: the 38 GST state codes, GSTIN validation, the Indian financial year (April–March), and amount-in-words in lakh/crore grouping.

  **Numbering** is a `DocumentCounter` row per (type, financial year), read and incremented inside the same transaction that issues the document, so two people issuing at once queue on the row rather than both taking `INV/2026-27/0001`. Drafts carry a `DRAFT-…` marker instead of a number: GST wants an unbroken serial, and a deleted draft must not leave a hole in it.

  **E-invoicing (IRP)** sits behind one `EInvoiceProvider` interface with two implementations. `mock` derives a real-shaped IRN locally (SHA-256 of GSTIN + doc type + number + FY, which is how the portal derives it too), so the whole flow — payload, storage, QR, cancellation — is exercisable without a portal account. `nic` calls the real NIC API, sandbox or production; the only difference is the base URL. The INV-01 payload builder (`src/lib/einvoice/payload.ts`) is the single place the portal's terse field names (`AssAmt`, `Pos`, `Stcd`) appear. `validateForEInvoice` returns one readable list of what's missing rather than letting the portal answer with a rejection code. A portal failure never loses the invoice: it stays issued, the error is stored and shown, and there's a Retry button. Cancellation is offered only inside the portal's 24-hour window, enforced in one shared helper so the button and the server agree.

  **Credentials** are encrypted at rest (`einvoicePasswordCipher`, `einvoiceClientSecretCipher`, via the existing `AUTH_SECRET`-keyed store) and never sent back to the browser — the settings form shows whether a secret is on file and leaves the field blank, so saving the page without retyping it doesn't wipe working credentials.

  **Organisation settings** (Settings → Organisation & e-invoicing, admin only) hold who Wroffy is on paper: legal name, GSTIN, state code, registered address, bank details, default terms, a signature/stamp image, and the IRP provider and credentials. The state code drives every tax split, so it falls back to the GSTIN's own first two digits rather than being left unset and silently taxing every sale as inter-state.

  **A schema addition this forced**: `CompanyLocation.pincode`. The IRP requires the buyer's PIN on every e-invoiced document and there was nowhere to put it. Added to the location form, the company-creation form, the test-data seed, and backfilled on existing seeded rows.

  **Two bugs worth recording.** The document form's line keys came from a module-level counter, but that module is instantiated twice — once on the server, which builds the starting draft, and once in the browser, which adds lines afterwards. The browser's counter restarted at 1 and collided with the server's first line, so editing one line edited both. Keys are `crypto.randomUUID()` now. Separately, the new-document page called `emptyDefaults()` from a `"use client"` module, which builds fine and fails at runtime — the draft builders moved to `src/lib/document-draft.ts`, which neither side owns.

  Verified live end to end: an intra-state invoice (₹3,23,500 subtotal, 5% discount on one line, CGST ₹28,892.25 + SGST ₹28,892.25, round-off ₹0.50, total ₹3,78,810) reconciled line-by-line against hand arithmetic; the IRP first refused it with "the customer's billing address is incomplete", which was true, and generated an IRN with a signed QR after the address was filled in; switching a customer's location from Bengaluru to Pune flipped the place of supply 29 → 27 and the tax from IGST to CGST + SGST; proposal → proforma → tax invoice and purchase order → vendor bill both converted with links in each direction; a credit note was raised against the issued invoice; the printable view renders as black-on-white outside the app shell with the QR, bank details, amount in words and signature block. `tsc` clean, `eslint` 0 errors, build compiles.

### Pagination and bulk actions on every list

  Every list screen in the app — 19 of them — now has server-side pagination with a page-size control (25/50/100/200, persisted in the URL). All but Orders and Tasks also have row selection and bulk actions suited to what the records are. Previously only `/items` had any of it.

  **Three shared primitives** (`src/components/ui/bulk-select.tsx`) rather than nineteen copies: `useRowSelection`, a `Checkbox`, and a `BulkBar` that each screen fills with its own actions. Selection is deliberately scoped to the rows on screen — with server-side pagination the component has never seen the other pages, so a "select all" that silently included them would be claiming more than it knows, and anything no longer in `rows` drops out when the page changes. `/items` had its own older implementation whose `Set` persisted across page changes, meaning a bulk action could act on rows the user could no longer see; it was migrated onto the shared hook.

  **Pagination** followed one pattern: each list query was split into a `somethingListWhere()` filter plus a `listSomethingPaged()` that reuses it and returns `{ rows, total }`. The unpaginated version stays for the places that legitimately need every row — the lead **board** (a kanban with a hidden page 2 misrepresents the pipeline), and the company/lead/ticket detail tabs. Header counts ("12 still onboarding", "3 open") became their own `count` queries over the same filter, so they don't shrink as you page. Two lists that derive their values in JS after the query — payment balances and renewal status — page in memory via `pageOf`, which the helper documents. The Payments screen has two independent tables, so `Pagination` grew `pageParam`/`pageSizeParam` props and the second one uses `ppage`/`ppageSize`.

  **Bulk actions per screen**: companies/customers/vendors/commission parties — assign caller, set onboarding status, add tags; leads — set owner, set status (with a required reason for lost/disqualified); contacts — set designation, delete; resellers — onboarding status and tier; tickets — assign agent, status, priority; documents — issue, set status, delete drafts; renewals — create renewal tasks; payments — delete.

  **Orders and Tasks are deliberate exceptions** — pagination only, no selection. An order's approval steps are judgements about that specific order (accounts weighs its payment terms, purchasing sources its vendor and cost), so approving a screenful at once would turn a review into a rubber stamp. Tasks are already one-click per row — the done checkbox, Edit and Delete are right there in the row — so a selection column on top of that is a second checkbox in the same table meaning something different, which is worse than no bulk at all.

  **The rule that shaped the implementation**: where an action has side effects, the bulk path calls the same single-record action in a loop rather than issuing one `updateMany`. A lead status change writes an activity entry, can flip the company to CUSTOMER and notifies the owner; a reseller going ACTIVE has to pass the onboarding gate that unblocks order punching; a ticket assignment notifies the agent. A bulk path that skipped those would make a record's history depend on how the click happened to be made. Records that can't change are counted as skipped and reported ("3 skipped — already reviewed"), rather than failing the batch. Tags are added, never replaced, so the button isn't a data-loss button wearing a helpful label.

  Verified live: all 19 lists render and paginate, 17 expose select-all (Orders and Tasks correctly have none); a 3-lead bulk status change to QUALIFYING wrote three correct `STAGE_CHANGE` activity entries ("from WON to QUALIFYING", "from CONTACTED…", "from NEGOTIATION…"); bulk tagging two companies preserved their existing `seed-test` tag; bulk renewal-task creation produced tasks with the right company, order reference, expiry-derived due date and assignee, and re-running it on the same rows created nothing (the open-task guard held). `tsc` clean, `eslint` 0 errors, build compiles.

### Field visits and expense management

  Two linked modules under a new **Field** nav group, plus a **Visits** tab on the company 360.

  **A visit** is planned with a purpose (11 of them, from intro meeting to payment follow-up), an agenda, a contact, an office and a date. On the day it's checked in, then completed with a write-up — the outcome is what makes a visit log worth keeping, so `completeVisit` requires it and `setVisitStatus` refuses to mark anything COMPLETED without going through that path. Cancelling or marking a no-show requires a reason. The form's contact, office and open-lead pickers load from the chosen company rather than shipping every company's down to the browser, and the address auto-fills from the selected office until someone types over it.

  **An expense** is a company expense, not just a travel claim: the model covers company-card software subscriptions and office spend as well as a salesperson's cab fare, which is what makes the Expenses menu the whole picture. Claims can attach to a visit (the company is then taken from the visit rather than trusted from the form, so a claim can't be filed against the wrong account), to a company directly, or to nothing at all. Receipts are stored as data URLs, capped at 512KB, PNG/JPEG/WebP/PDF.

  **The approval chain** routes to the claimant's manager — the `managerId` reporting line that already existed for permission inheritance. The approver is snapshotted onto the row at submit time, so a later reporting-line change can't move a claim mid-review. Nobody can approve their own claim, whatever permissions they hold. Four new permissions: `expenses.approve` (an override for covering an absent manager, or a claimant with no manager), `expenses.reimburse`, `expenses.viewAll` and `visits.viewAll`.

  **Status is deliberately five states, not four.** DRAFT is the claimant's own scratch space — nothing is in anyone's queue until SUBMITTED. REIMBURSED is separate from APPROVED because a manager saying yes and accounts actually paying it out are different events on different days, and collapsing them would make "what do we owe our staff" unanswerable. That figure — approved **and** reimbursable — is the Expenses page's "Payable now" card, and it's why `reimbursable` is a field: company-card spend was never out of anyone's pocket, so a flat expense total can't tell you what's owed.

  **Visibility is scoped.** An expense claim is somebody's money and a visit log is a record of where someone spent their day, so neither is company-readable by default: you see your own and your team's, and the `viewAll` permissions open the rest for company-wide reporting. The one exception is that an approver can always open a claim routed to them, even when the claimant isn't in their downline.

  **A gap found while testing, and closed.** The first claim was raised by an admin with no reporting manager, so it routed to nobody — and since nobody can approve their own claim, it was unapprovable. `resolveApprover` now falls back to an active user holding `expenses.approve` (never the claimant), and where even that finds nobody, the claim says so plainly instead of "waiting on your manager". Separately, `visitDuration` returned null for a sub-minute visit, which rendered as an em dash indistinguishable from "never checked in"; it returns 0 now, so "0m" means short and "—" means unrecorded.

  Verified live across three sign-ins: planned a product-demo visit with dependent pickers and an auto-filled address, checked in, completed it with a write-up, claimed ₹1,240 travel against it; as a salesperson raised a ₹860 fuel claim which routed to her manager, confirmed she had no approve/reject on her own claim and could not see the admin's; as that manager approved it and marked it reimbursed with a UTR; as Accounts (holding the override) saw every claim, confirmed Reject stays disabled without a note, and rejected one with a reason that surfaced back on the claim. ### Dropdown panels escape their scroll container

  The catalogue picker in a document's line-items table was being cut off mid-list. The cause is a
  CSS one worth writing down: the table sits in `overflow-x-auto` so wide documents scroll
  sideways, but setting `overflow-x` alone makes the browser compute `overflow-y: auto` as well,
  and an absolutely-positioned panel inside is then clipped at the container's edge.

  `AnchoredPopover` renders the panel into `document.body` and positions it `fixed` against its
  anchor, which sidesteps clipping entirely. A portalled panel doesn't move with its anchor for
  free, so it tracks scroll (with capture, to catch scrolling ancestors, not just the window) and
  resize, and flips above the anchor when there isn't room below. Both the item picker and
  `CompanyCombobox` use it — the combobox gets used inside table rows and scrollable panels too,
  and would have hit the same wall.

  Portalling costs the thing that was previously free: a panel outside the input's subtree means
  `onBlur` no longer closes it, and a click inside the panel would count as "outside". Both
  components now close on an explicit outside-mousedown check that exempts the panel, and on Escape.

  Verified live: the panel is a child of `<body>`, no ancestor clips it, it sits fully inside the
  viewport, and picking an item still fills the row's description, unit, price and tax rate.
  Selecting a company still drives the dependent logic — place of supply and the CGST/SGST-vs-IGST
  split on a document, contacts/offices/leads on a visit.

### Accounting core: invoices are what money settles against

  First slice of making the sales/accounting side work the way Zoho Books does. The structural
  problem it fixes: payments allocated to **orders**, so an invoice had no notion of being paid. An
  invoice is the unit everything hangs off in any ledger — payments apply to it, credit notes offset
  it, and aging and statements are derived from it — so nothing else could be built until that was
  true here.

  **Settlement.** `PaymentAllocation` gained an optional `documentId` alongside its existing
  `companyProductId`: one allocation ledger, pointing at either an order (the original punch flow,
  untouched) or an invoice. Exactly one, enforced in the action, since a row settling both would be
  counted twice. `CreditNoteApplication` is its own table rather than a negative payment — no money
  moved, the customer owes less, and conflating them makes "received" a lie.

  **Status is derived, never nudged.** `settledStatus()` computes ISSUED / PARTIALLY_PAID / PAID
  from what's been applied, and `syncInvoiceStatus` re-derives after every application. A stored
  status edited by hand is the usual way an invoice ends up marked PAID with money still owed.
  Balance never goes below zero either: an overpayment is credit on the account, not negative debt,
  and letting it go negative would quietly cancel out genuinely overdue invoices in the aging total.

  **Aging** buckets from each invoice's own due date — falling back to the issue date, because
  treating a no-due-date invoice as never-due hides real debt. Computed in memory rather than SQL
  since the bucket depends on each invoice's date against today.

  **A contradiction caught in review.** The first statement showed "Outstanding ₹0.00" beside a
  closing balance of −₹2,50,000. Both were correct and they measure different things — what's still
  owed on invoices, versus what's sitting unapplied on account — but side by side they read as a
  bug. The statement now breaks out unapplied payments and unapplied credit notes, states the net
  position in words, and labels the running balance so a negative figure reads as "in credit".

  **New: Receivables** (aging report per customer, bucketed and totalled) and a **Statement** tab on
  every customer (figures, aging, open invoices with days overdue, and the full running-balance
  ledger of invoices, payments and credit notes).

  Verified live end to end on one invoice: recorded a ₹2,00,000 part payment against ₹3,78,810 —
  balance recomputed and status auto-flipped to Partially paid; a ₹5,00,000 attempt was refused
  with "Only ₹178810.00 is outstanding"; issued the linked credit note, applied it with the amount
  defaulting to the smaller of credit-remaining and invoice-balance (₹1,78,810, not the full
  ₹3,78,810), leaving ₹2,00,000 unapplied; the invoice then read Settled in full and derived to
  **Paid**. Aging verified with five backdated invoices across every bucket — each landed in the
  right one, per-customer and column totals reconciled (₹3,75,000 total, ₹3,25,000 overdue), and
  the test data was removed afterwards.

### Documents rebuilt to match Zoho Books

  The document form now has the structure Zoho Books uses, because that's the shape people raising
  quotes and invoices already know.

  **Addresses are snapshotted onto the document**, not referenced from the customer. Despatch-from,

  rejects it outright.

  **Numbering is configurable per document type** — prefix, next serial and zero-padding, with

  at 1 and immediately proposes a number already in use — the uniqueness guard refused it, correctly
  but uselessly. `startingSerial()` now seeds a fresh setting past the highest trailing number
  already issued, so it picks up where the previous scheme left off.

  **Line discounts take a percentage or a flat amount**, with the resolved rupee figure stored so a

  **Document-level: shipping charges** (taxed at their own rate and joining the taxable value, since

  **adjustment**. Round-off became an organisation preference: usual on an Indian invoice, but Zoho
  leaves it off and some businesses bill to the paisa.

  exist.
- **Public edges** (`/preferences/<token>`, `/forms/<slug>`, `/track/<token>`): same 192-bit token
  and identical-refusal pattern as the feedback form, except a preference token is long-lived —
  an unsubscribe link that has gone stale is not an unsubscribe link.
- **Consent** as a DPDP artefact per channel and topic, with source, evidence and a withdrawal
  timestamp rather than a deletion. SMS is deliberately out of scope: TRAI DLT registration is a
  prerequisite, not a feature.
- Verified by `npm run check:marketing` (~130 assertions) and `npm run db:seed:marketing`, which
  plants a fully opted-in reseller-managed company inside the audience and proves it comes out

### Document lists as a master-detail split view

  The document lists read the way Zoho's do, because the job is nearly always "scan the list, open
  one, act on it, go back" and a full page navigation per document makes that four steps instead of
  one.

- **Split view.** Clicking a document's number on any list opens it *beside* the list rather than
  navigating away: a 340px pane of rows on the left (customer and amount on one line, number and
  date under it, status badges under that) with the full document in the right pane. Selection
  lives in `?doc=<id>`, so an open document is a link somebody can send, not component state. A
  `?doc=` that isn't on the current page — a stale link, or a filter that has since excluded it —
  falls back to the plain table instead of showing an empty pane.

- **`DocumentDetail` is shared.** `src/components/documents/document-detail.tsx` renders both the
  standalone `/documents/[id]` page and the split view's right pane; `embedded` only drops the
  back-link and the page animation. The page itself is now a seven-line wrapper, so the two can't
  drift apart.

- **Details / PDF tabs.** The right pane toggles between the working view and a preview of what
  prints (`?view=pdf`). The preview renders the print page at its real 820px width and CSS-scales
  it to fit (`document-pdf-preview.tsx`) — dropping the print page into a narrow iframe would let
  it reflow, and a preview that lays out differently from the PDF isn't a preview. The print page
  takes `?embed=1` to drop its own print button inside that frame.

- **One toolbar instead of scattered buttons.** `DocumentActions` is now a single row — the action
  that moves the document forward first (Issue, or Print/Convert once issued), then everything else
  behind a **More** menu (mark-as statuses, cancel e-invoice, delete draft). New `Menu`/`MenuItem`
  primitives in `src/components/ui/menu.tsx`, built on `AnchoredPopover` (which gained
  `align="end"` for right-aligned panels).

- **"What's next?" banner.** `src/lib/document-next-step.ts` turns a document's state into the
  action it implies — a draft says nothing has been sent yet, an issued invoice says how much is
  outstanding and whether it's overdue, an accepted quote says to convert it, a credit note says
  how much is still unapplied. A status badge says *where* a document is; it doesn't say what to do
  about it, and a draft invoice and an overdue one look equally inert on a badge.

- **Salesperson is a real field.** `TradeDocument.salespersonId` (migration
  `20260917113000_document_salesperson`), defaulting to the company's owner and inherited through
  conversions, so converting a quote doesn't reassign the deal to whoever pressed the button.
  Existing documents were backfilled from `Company.ownerUserId`. It replaces "Created by" as a list
  column (created-by is still on the detail's Record card) and is editable on the form.

- **List columns follow the Zoho order**: Date, Number, Reference #, Party, Status, Amount,
  e-Invoice, Salesperson. Reference # got its own column instead of being a sub-line under the
  number.

- **A line has a name and a description.** `TradeDocumentLine.description` used to hold the item's
  *name*, which made every read of it a small lie and left nowhere for the free text a quote
  usually carries — what's included, the period covered, serial numbers. Renamed to `name`, with a
  nullable `description` beside it (migration `20260917130000_line_name_and_description`). The form
  shows it as a textarea under the item, seeded from the catalogue item's own description and
  editable per document. Both the detail and print views render it under the name with
  `whitespace-pre-line`, so three typed bullet points arrive as three lines on the customer's copy.
  The e-invoice payload joins the two, since the portal takes one description per line.

- **The detail sizes itself to its container, not the window.** `DocumentDetail` is
  `@container` and its two-column split is `@4xl:`, not `lg:` — a viewport breakpoint says nothing
  about how much room a component actually got, so in the split pane the old `lg:grid-cols-3` still
  fired and squeezed the items table into a horizontal scrollbar. The items table folds HSN and
  Taxable away below `@2xl` and re-shows them under the description and in the total cell, so a
  narrow pane loses no information and gains no scrollbar.

- **Fixed while building this**:
  - A rejected or cancelled document used to hide its own "Mark as" menu, so a mis-click was
    permanent as far as the UI was concerned even though the server allows the reverse.
  - The nav sidebar had `overflow-y-auto` on its `<nav>` but no height on the `<aside>`, so it grew
    to fit every item and dragged the whole page taller — the nav never scrolled on its own and the
    window scrolled instead. It's now `md:sticky md:top-0 md:h-screen`, which is what that
    `overflow-y-auto` was always meant to work with. This is why the split view showed a window
    scrollbar next to the pane's own.
  - The split grid carries the `calc(100vh-12.5rem)` height rather than each pane, so its borders
    come out of that figure instead of being added to it and the page doesn't scroll by two stray
    pixels. The panes get `min-h-0`, without which a grid item grows to fit its content instead of
    scrolling.

### Split view on every list, with the choice left to the user

  Ten lists now offer the same two layouts — the full table, or a narrow list with one record open
  beside it: Companies, Customers, Vendors, Resellers, Commission parties, Leads, Orders, Renewals,
  Tickets and the six document types.

- **The choice is remembered per list, in a cookie** (`wroffy.view.<key>`, read by `getViewMode` in
  `src/actions/view-mode.ts`). Per list rather than globally because the same person often wants the
  table for Leads and the split for Invoices. A cookie rather than the URL so it survives navigation
  and sharing a filtered link doesn't impose your layout on whoever opens it; read on the server so
  the first paint is already in the chosen layout rather than flashing the table and swapping.

- **`ViewModeToggle`** (`src/components/ui/view-mode-toggle.tsx`) sets it. Leads has its own
  three-way Board / Table / Split control instead: board-versus-list stays in the URL because
  they're genuinely different views of the pipeline and a link to the board should open the board,
  while table-versus-split is the same layout preference as everywhere else.

- **`?sel=<id>`** names the open record, so a particular record in the split view is a link somebody
  can send. `resolveSelected` falls back to the first row when the id isn't on the current page — a
  stale link or a filter that has since excluded it — rather than showing an empty pane beside a
  list that doesn't contain it. The documents list moved from its old `?doc=` to this shared param.

- **Detail components are shared, not duplicated.** Each `[id]/page.tsx` became a wrapper around a
  component the split view also renders: `CompanyDetail`, `LeadDetail`, `OrderDetail`,
  `TicketDetail`, `DocumentDetail`. Five of the ten lists are really lists of companies, so
  `CompanyDetail` serves all five; a renewal row *is* an order, so `OrderDetail` serves Renewals too.
  That leaves four detail components behind ten lists.

- **`CompanyDetail` takes `basePath` and `linkParams`** so its tabs stay put when embedded — a tab
  link goes back to the list with the filters and the selection intact (`/vendors?q=Kinetic&sel=…&tab=visits`),
  not off to `/companies/<id>`.

- **Every detail is a container, not a viewport reader.** The first pass shipped the split view with
  each detail still laying itself out from `sm:`/`lg:` breakpoints, which measure the window — so in
  a ~650px pane on a 1440px screen the company header crammed its name, badges and half its controls
  into one non-wrapping row (the name wrapped underneath the pills), six stat cards squeezed
  `₹42,36,000.00` into a truncation, and the lead detail sat at a hard-coded `grid-cols-3`. Each
  detail root is now `@container` and its internal layout asks how much room *it* got:
  `@3xl` (768px) for a main-plus-sidebar split, `@xl`/`@5xl` for the company's stat row, `@lg` for
  label/value columns. The company header also separates identity (name, badges, location, tags) from
  controls, which now wrap together as one group instead of being split across two places.

- **Label/value rows wrap instead of colliding.** 57 of them were `flex justify-between` with no gap
  and no shrink control, so the label and value ran into each other as soon as a column narrowed and
  a long value wrapped under itself while the label stayed put. They're now
  `flex flex-wrap items-baseline justify-between gap-x-3` — the value drops to its own line when it
  can't share one, which is what a container query would do without needing to know the width.

- **`TabNav` wraps rather than scrolls.** The company 360 has thirteen tabs and a scrolled strip hides
  them with no hint they exist. This is navigation, so you have to be able to see what's there.

- **`SplitListShell` must be a direct child of `SplitListPage`.** It sizes itself with `flex-1`,
  which means nothing unless its parent is the flex column — on Customers, Vendors and Commission
  parties it was wrapped in a plain `<div className="mt-6">`, so the page's height never reached it
  and the list pane grew to fit every row (73 customers tall, with the whole page scrolling). Fixed
  by lifting the conditional out of the wrapper, and the shell now also carries
  `lg:max-h-[calc(100vh-7.5rem)]` as a backstop: when it *is* a flex child, `flex-1` computes a
  smaller height and wins; when it isn't, the cap stops it running away.

- **`SplitListPage` + `SplitListShell` size to what's left**, rather than subtracting a guess at
  what's above. A list with three rows of filters has far less room than one with a bare heading, so
  the page is a viewport-height flex column and the shell is the part that flexes. The only fixed
  figure is the app shell itself — the 56px header plus `main`'s padding.

- **Fixed while building this**: `listRenewals` used `include`, which brings the whole
  `CompanyProduct` row along including its `Decimal` money columns, and the renewals table is a
  client component — so every renewals page load was logging "Only plain objects can be passed to
  Client Components". Pre-existing; `toPlain` at the action boundary fixes both layouts. Button
  labels no longer wrap mid-phrase, and `TabNav` scrolls instead of clipping its last tab.

### General ledger

  Double-entry books, with postings raised automatically as documents are issued. `LedgerAccount`,
  `JournalEntry` and `JournalLine` (migration `20260917105304_general_ledger`).

- **The posting engine is pure** (`src/lib/ledger/posting.ts`). It takes a document's figures and
  returns balanced lines keyed by *system account* rather than id, so it can be reasoned about and
  tested without a database. `npm run check:postings` runs it over every issued document plus nine
  synthetic scenarios built through the real GST engine — TDS, TCS, freight, negative round-off,
  no-rounding — and asserts each of the 27 resulting entries balances and that no line carries both
  a debit and a credit.

- **`withholdingAmount` is signed** in the GST engine: negative for TDS, positive for TCS. The
  posting engine reads that sign rather than re-deriving it from the mode, because two places
  deciding the direction is two places to disagree. TDS on a *sale* is an asset we later claim
  (the customer paid it to the government for us); on a *purchase* it's a liability (we withheld it
  and owe it onwards). Those are different accounts, which is why `TDS Payable` exists alongside
  `TDS / TCS Receivable`.

- **Accounts are found by `systemKey`, not code or name.** A business will renumber its chart and
  rename "Sales" to whatever its accountant prefers; neither should stop an invoice posting.
  Accounts carrying a key can be renamed and renumbered but not deleted or archived.

- **Posting happens inside the caller's transaction.** `src/lib/ledger/journal.ts` is deliberately
  *not* a `"use server"` module — its functions take a Prisma `TransactionClient`, which can't cross
  a server-action boundary, and exporting them as actions would publish them as endpoints with no
  auth check. Issuing a document and posting it commit together, so a document can't reach a
  customer without its entry.

- **Nothing is edited or deleted.** A cancelled document is reversed: the original entry stays in
  the journal with a dated reversal beside it. Reversals can't themselves be reversed.

- **Reports** are trial balance, P&L and balance sheet, each drilling into an account ledger with a
  running balance. Retained earnings is *computed* (income less expenses for all time) rather than
  posted by a year-end closing entry, which would be a second figure that can drift from this one.
  Every statement states plainly whether it balances rather than leaving the reader to add columns.

- **Payables now mirror receivables.** `Payment.direction` distinguishes money in from money out, so
  a vendor bill settles the way an invoice does. `/payables` ages what we owe using the same buckets
  as `/receivables` — a business says "over 90 days" the same way whichever direction the money is
  going, and two scales would make the reports impossible to read side by side.

- **`npm run ledger:backfill`** posts documents and payments that predate the ledger. Idempotent.

- **Found by the end-to-end test, not by reading the code**: `cancelEInvoice` set the document's
  status directly rather than going through `setTradeDocumentStatus`, so cancelling an e-invoice
  left its revenue in the books. `check:postings` now also checks for drift — issued documents with
  no entry, cancelled documents with a live one, and entries that don't balance in the database.

### Calling

  A phone icon on every record a caller works from, and one screen the calling team lives on.
  `CallLog` (migration `20260917…_call_logs`), module key `calls`.

- **Nothing dials.** The button is a stopwatch: start, stop, resume. An earlier version fired a
  `tel:` link, which launched whatever handler the machine had registered — not wanted, because the
  call is placed on a phone and the app only has to time it. Every `tel:` link in the product is now
  gone, including the two that predated this (the company's contacts list and the contacts library),
  which both go through the call dialog instead: dialling without logging is the thing a calling CRM
  exists to stop.

- **The timer is real, not remembered.** Duration comes from the stopwatch rather than from someone
  estimating afterwards. Only the first start resets the clock — stopping and starting again
  resumes, so a pause to look something up doesn't throw away the minutes already on it, and a
  Reset is there for when the timer was started by mistake.

- **Outcomes are more than connected/not.** "Wrong number" and "not interested" mean very different
  things for whether to try again, and `CONNECTED_OUTCOMES` is what the connect rate is computed
  from — dialling 80 numbers and reaching four people is a very different day from reaching forty,
  which a raw call count hides completely.

- **Callbacks are a worklist.** "Callback requested" requires a time, because a promise with no time
  on it is one nobody keeps. Those land on `/calls?view=due`, soonest first, and are closed by
  marking them done rather than by deleting the promise.

- **A callback raises a task and rings a bell.** Setting a callback time creates a `Task` assigned
  to *whoever made the promise* — a callback is owed by the person who gave their word, not by
  whoever owns the account — due at that time, titled after the contact and company, linked to the
  company and to the lead or ticket the call was about. `CallLog.followUpTaskId` is a one-to-one
  link, and closing either side closes the other: tick the task and the callback closes, press Done
  on the callback and the task closes. Reopening works the same way, for the mis-click.

- **The reminder fires to the minute.** `syncSystemNotifications` gained a `CALLBACK_DUE` candidate
  deduped on the call id. The existing task sweep works at day granularity, which isn't good enough
  here — a callback agreed for 3pm is late at 3pm, not at midnight. That sweep now also *excludes*
  tasks raised by a callback, because otherwise the caller got two bells for one promise: a generic
  "Task due today" and the better "Callback due" that names the person and links to the callbacks
  list. There's still no background job runner, so this fires on the next notification fetch — it
  reaches someone using the app, not someone who has closed it.

- **A call always belongs to a company**, and optionally to the lead, ticket or subscription it was
  about — so a call placed while working a renewal shows on that renewal, not just somewhere in the
  company's history. A call against a lead also writes to that lead's existing `Activity` timeline,
  so the lead page doesn't suddenly have two places to look.

- **Where the icon is**: the company 360 header (which covers Companies, Customers, Vendors,
  Resellers and Commission parties), each contact row, lead detail, ticket detail, and the order
  detail that Renewals opens. Plus a **Calls** tab on the 360 for that company's history.

### Domain Intel

  What public DNS and a company's own website say about them, and what that leaves open for a sale.
  `DomainProfile` (migration `20260917140000_domain_profile`), module key `domains`, shown on the
  Details tab of any company — so Companies, Customers, Vendors, Resellers and Leads all get it —
  plus its own prospecting list at `/domains`.

- **Nothing is fetched until someone asks.** A lookup makes a dozen outbound requests — MX, NS, TXT,
  DKIM selectors, the homepage, RDAP — and takes seconds. It runs on a button and the answer is
  cached with `fetchedAt` on screen, so a stale reading can't be mistaken for a current one. Loading
  a company page fetches nothing; that was verified by clearing the table, loading the company list
  and confirming the count stayed at zero.

- **Public resolvers, deliberately.** `dns.resolveMx` and friends use whatever c-ares was handed at
  startup, which on this laptop was a stub at 127.0.0.1 with nothing listening — every lookup came
  back ECONNREFUSED, which the code read as "this domain publishes no MX". Badly wrong and silent.
  A dedicated `Resolver` now points at 1.1.1.1/8.8.8.8 (`DNS_RESOLVERS` overrides). Everything looked
  up is a customer's public domain, so public resolvers are the right answer regardless.

- **The rules are pure and carry their evidence.** `signatures.ts` turns records into facts —
  MX → mail provider, MX/SPF → security gateway, HTML+headers → platform, headers/CNAME → host — and
  each platform match reports *why* ("wp-content in the markup"), because a rep will repeat whatever
  this screen says on a call and needs to be able to check it. Matching is conservative: saying
  nothing beats saying "WordPress" about a site that merely links to one.

- **`opportunities.ts` is the point of the module.** It turns the findings into an observation and
  an angle — Google Workspace is an M365 comparison, self-hosted mail is a migration, DMARC p=none
  is someone who started and stopped, a domain expiring inside 90 days is when someone reviews what
  else is on that invoice. Observation first, because a rep who leads with the fact sounds informed
  and one who leads with the pitch sounds like a cold call.

- **Free services only.** RDAP (`rdap.org`) for registrar and expiry, no key. Screenshots via
  WordPress mShots by default, overridable with `DOMAIN_SCREENSHOT_URL` for a paid renderer. No
  image is stored — the URL is saved and the browser fetches it, via a plain `<img>` so a
  third-party host doesn't have to be listed in `next.config`.

- **Verified against real domains** rather than fixtures: wroffy.com reads as Microsoft 365,
  WordPress on LiteSpeed, GoDaddy expiring Sept 2027, SPF present, **DMARC p=none** — which is a
  genuine finding about Wroffy's own domain and worth acting on.

### Workspace

  Saved lists built from filters — a territory, a renewal window, every account nobody has called in
  90 days. `Workbook` (migration `20260917150000_workbook`), module key `workspace`.

- **The filters are saved, not the rows.** A list called "Maharashtra, no order in 90 days" still
  means that next month, rather than freezing whoever matched on the day it was built. That's what
  makes it usable for lead gen and account management; a snapshot would go stale immediately.

- **`filters` is JSON, not columns.** The useful filters change as the business does, and a
  migration per filter means nobody ever adds one. `buildWhere` ignores keys it doesn't recognise,
  so a list saved against a filter a later release drops degrades to a broader list rather than
  erroring.

- **Around thirty filters**, grouped the way someone thinks about a list rather than by which table
  the column lives in: who they are (relationship, stage, industry, city, state, category, tags,
  employee range, source), who owns them (account manager, caller, unassigned), what they've bought
  (has orders, order type, order status, unpaid invoice), renewals (expiring within 30/60/90/180,
  expired), pipeline (lead status, open lead, **every lead lost**, never had a lead), engagement
  (not called in N days — which counts never-called, added between), and what their domain says
  (email provider, platform, spoofable, not yet looked up). The last group is Domain Intel feeding
  the list builder.

- **A list is assigned to the people who will work it.** `WorkbookAssignee` (migration
  `20260917160000_workbook_assignees`) — a join table rather than an array of ids, because "which
  lists am I on" has to be a real query and an array can hold ids of users who no longer exist. The
  whole set is chosen at once rather than added one at a time, since assignment is thought about as
  "these three people" and a bare add makes removal a second, forgotten step. Anyone newly assigned
  is notified with the note; people already on it aren't notified again. `/workspace` puts
  **Assigned to you** above everything else, because a caller opens that screen to find their work.

- **Product and brand filters.** Brand, product family, specific product and item type all narrow
  through the orders relation, and `productExcludes` flips the question: "customers who have never
  bought Autodesk" is the cross-sell list, and is asked at least as often as "who has". The product
  dropdown only lists items somebody has actually ordered — filtering on a product nobody bought
  returns nothing, which reads as the builder being broken rather than the filter being right.

- **Split view on a saved list**, the same as every other list: clicking a company opens the full
  360 beside the narrow list, with `?sel=` deep-linking and the Table/Split choice remembered under
  the `workspace` key. The description and filter chips hide in split mode — they're read once, and
  in split mode the header is competing with the record for height.

- **The running match count is the point of the screen.** Debounced at 350ms, it's what tells
  someone a filter is too narrow *before* they save it and hand it to a rep. Preview and saved view
  run the same `runWorkbook`, so what you saw when saving is what you get back.

- **Shared by default, editable by its owner.** A list everyone can see but only its author can
  redefine — otherwise one person's working list gets changed out from under them. Duplicate makes
  your own copy to narrow.

- **Found by testing, not by reading**: city and state match on *any* of a company's locations, but
  the results table showed only the primary one — so a Gurugram head office appeared under a
  Maharashtra filter and a correct match read as a bug. The row now shows the site that actually
  matched, labelled "2 sites · this one matched".

### Calling activities

  A saved list can become a campaign: the rows are frozen, shared out between callers, and worked
  through one at a time with the timing recorded. `WorkbookRecord` and `ContactVerification`
  (migration `20260917170000_calling_activity`).

- **Starting an activity freezes the rows.** A saved list is a live segment, which is right for
  browsing and impossible to hand out as work — a caller can't be measured against a set that
  reshuffles underneath them, and two callers can't safely share one. Starting materialises the
  current matches into records, and everything after that is about those records rather than the
  filters. That closes the "live segment, not a work queue" gap recorded earlier.

- **Three allocation methods** in `src/lib/workspace/allocation.ts`, pure so the split can be read
  and checked without a database: round robin, equal blocks (remainder spread one-per-caller so the
  biggest and smallest shares never differ by more than one), and to-the-account-owner with round
  robin for the unowned. The split is previewed before anything commits, because starting is not a
  step anyone wants to discover was wrong afterwards. Re-sharing mid-campaign only moves *unworked*
  records — reassigning something already called would strip the caller of the credit and make the
  timing meaningless.

- **Each caller gets a task with the deadline**, so the work turns up where they already look, and
  finishing the last record closes it without anyone remembering to tick it.

- **Timing is two figures, not one.** `handleSeconds` is how long a record took; `gapSeconds` is the
  silence before it. A slow day is either long calls or long gaps and the fix differs, which a
  single "average per record" would hide. The gap is capped at 30 minutes (`MAX_TRACKED_GAP_SECONDS`)
  so going home at six and starting at nine doesn't register a fifteen-hour idle that swamps every
  real figure. Reported per caller and per day.

- **The calling screen shows almost nothing.** Company, where they are, size, the contacts with
  their numbers, a call button. Everything the 360 view carries is noise to somebody working through
  two hundred numbers, and the full record is one click away for the rare case it matters.

- **A correction never touches the contact.** `ContactVerification` keeps the original *and* the
  corrected value with who said what and when; `/verifications` is where somebody accepts or rejects
  it. A number corrected on a call is a claim — people mishear digits, reach the wrong person, or
  "fix" a number that was right for a different branch — and the calling screen is the one place in
  the app where people type fast under pressure. Verified end to end: after saving a correction the
  contact's phone was unchanged and both values sat on the verification row with `appliedAt: null`.

- **Found by the compiler, again**: the calling screen reset its note and stopwatch from an effect,
  which the React compiler rejects (`set-state-in-effect`). Per-record state now lives in children
  keyed by record id, so moving on remounts them fresh — and the ticking clock no longer re-renders
  the contact rows and their half-typed corrections every second.

### Outgoing links and email verification

- **Every link out of the ERP strips its referrer.** `OutboundLink` (`src/components/ui/outbound-link.tsx`)
  is now the only way an off-site URL is opened: it sets `target="_blank"`, `rel="noopener noreferrer"`
  and `referrerPolicy="no-referrer"`. Without it, clicking through to a prospect's website or LinkedIn
  hands the far end a `Referer` of `/companies/<id>?tab=domain` — which tells their web server, their
  analytics and anyone who later reads those logs that somebody at Wroffy was looking at them and which
  record they were on. That is pipeline leaking through a request header. The third-party homepage
  thumbnail in Domain Intel carries the same attribute for the same reason: the browser fetches it
  directly from the screenshot service.

- **`npm run check:links` enforces it.** A rule this easy to state is exactly the kind that decays, so
  `scripts/check-outbound-links.mjs` fails on a raw external `href`, a `target="_blank"` that isn't
  same-origin, or a third-party `<img>` without the policy. Verified by planting a violation and
  watching it fail.

- **Every email address carries the state of its last check.** `EmailAddress` / `EmailCheckBadge`
  (`src/components/contacts/email-address.tsx`) sit beside the address on the company 360, the contacts
  table, the calling station and the visit record. Unchecked is a button that runs the check; anything
  already checked opens what was found, when and by whom, with Check again / It works / It's wrong.
  Bulk paths: every address at one company, or any selection on the contacts table.

- **What the check can and cannot prove is the whole design.** `checkEmailAddress` validates the shape,
  rejects disposable domains, and reads MX — falling back to an A record, which RFC 5321 still treats as
  a mail destination and small Indian hosting packages still rely on. It reaches VALID, RISKY (a role
  inbox like `info@`, or a personal gmail) or INVALID. It deliberately does **not** open an SMTP session
  and issue RCPT TO: Microsoft 365 and Google both answer 250 for mailboxes that do not exist, many
  hosts greylist an unknown sender, and probing at volume from an office IP is how that IP lands on a
  blocklist and this business loses its own outbound mail. So a machine check tops out at
  VALID/AUTOMATIC, and CONFIRMED is reserved for a person who actually reached the human.

- **A verdict belongs to the address, not the contact.** `emailCheckedValue` stores the exact string the
  check ran against, and `emailCheckState` compares it with the current `email` before showing anything.
  Editing an address therefore cannot inherit the previous green tick — through the form, an import or
  an accepted correction — without every one of those paths having to remember to clear the fields.
  Verified by changing an address in SQL behind a CONFIRMED verdict: the badge dropped to "not checked"
  with "the address changed since it was last checked", while the row still read VALID. The counters on
  `/verifications` apply the same rule through a Prisma field reference, so they agree with the badges.

- **The two verification systems feed each other.** A caller marking an email Right on the calling
  station records CONFIRMED on the contact; marking it Wrong records REPORTED — neither touches the
  address itself. Accepting a correction in the review queue writes the new address already CONFIRMED,
  because someone at the company read it out and a reviewer accepted it, which beats any DNS lookup. A
  corrected email that isn't a complete address is now rejected at capture, while the caller still has
  the person on the phone, rather than three days later when nobody can recover the missing half.

- **Found while wiring it up**: importing the checker into the badge pulled `node:dns/promises` into the
  browser bundle and panicked Turbopack outright. The rules now live in `email-verification.ts` (pure,
  shared with the client) and the resolver work in `email-verification-lookup.ts` (server only). The
  shared DNS resolver moved to `src/lib/dns.ts` so the "never use the machine's own resolver" lesson
  is not configured twice. Redaction was extended too: a reseller-managed contact loses
  `emailCheckedValue` and `emailCheckDetail` along with `email`, or the redacted address would sit in
  the next field along.

## Known gaps (flagged, not silently skipped)

- **AR reads heavily credit on the seed data.** Payments allocated to *orders* post to Accounts Receivable for a customer with no invoice — so they sit as a credit, which is how Zoho and Tally show an unapplied receipt too, but with 40 order-payments against 3 invoices in the test data the balance sheet shows AR at about −₹2.5 crore. Arithmetically correct and the statements still balance; it's the order-versus-invoice split below surfacing in the GL, and it resolves as orders get invoiced. A real fix is either invoicing from orders or posting order receipts to an "Advance from Customers" liability.
- **Stale-closure toggles, found by testing**: the assignee picker and the filter chips both built their next value from a `selected`/`filters` captured in the render closure, so two clicks inside one tick read the same value and the second overwrote the first — picking two people quickly kept one. Both now use functional updates. Worth watching for in any other multi-select added later.
- **A calling activity is one-way.** Once started, a workbook is a campaign for good — there's no "stop and go back to being a segment", and no way to add newly-matching companies to a running activity. Both are deliberate (the frozen set is what makes the numbers mean anything) but a long campaign will drift from the filter that created it.
- **Timing assumes one record at a time.** The clock starts when a record appears on screen, so a caller who opens the queue and walks away records that as handle time. There's no idle detection and no pause button.
- **An email check proves the domain, not the mailbox.** VALID means mail to that domain is accepted;
  it cannot tell you the person still works there, or that the address was ever right. Only a reply
  does, which is why CONFIRMED is a separate state a human sets. There is now a bounce feedback loop — a hard bounce reported to `/api/marketing/webhook/[provider]` writes a suppression *and* sets the contact INVALID with method REPORTED. Before the marketing module there was none
  either — nothing in the app sends mail yet, so nothing can learn from a bounce.
- **Nothing checks addresses on a schedule.** Verification happens when someone presses a button: one
  contact, one company, or one selection. A nightly sweep over 500 contacts would be cheap (the MX
  cache collapses a whole company to one lookup) and there is now a scheduler (`/api/marketing/tick`, called from outside the app) that could drive one, though nothing yet schedules re-checks, so an address
  checked today stays green until somebody checks it again.
- **The disposable and free-mailbox lists are hand-maintained.** Twenty throwaway domains and twenty
  consumer providers, chosen for what this business actually meets. A throwaway domain that is not on
  the list reads as an ordinary company domain.
- **`billedMin`/`billedMax` are defined but not wired.** Filtering on invoiced value means summing each company's invoices, which Prisma can't express in a `where` — it needs a raw query or a stored total on the company. `isPostFilter` marks them so the gap is visible in code rather than silently returning everything.
- **Domain Intel reads, it doesn't enrich.** Employee count, industry and LinkedIn come from the company record as typed, not from an enrichment provider — the module only reports what DNS and the company's own homepage publish. There's no bulk "scan everything" either: lookups are one company at a time, on purpose, because a few hundred outbound requests in a loop is how an IP gets rate-limited.
- **A callback reminder only reaches someone who has the app open.** It fires on the next notification fetch, standing in for a cron the way the rest of the system-notification sweep does. A callback promised for 3pm reaches a caller who is working at 3pm, and waits for one who isn't.
- **Calls are logged, not placed.** By design — the app times the call, it doesn't make it. So there are no recordings, no duration from the carrier, and inbound calls only appear if someone logs them. A click-to-call provider (Exotel, Knowlarity, Twilio) would close all three, and `CallLog` is already the right shape to receive that data; that would be a real integration rather than a `tel:` hand-off.
- **Expense claims don't post yet.** `postExpenseClaim` exists in the posting engine and `EMPLOYEE_PAYABLE` is in the chart, but approving a claim doesn't raise an entry — expenses reach the P&L only when they arrive as a vendor bill.
- **No period close.** Nothing stops a journal entry being dated into a month already reported on. Reversals default to today's date rather than the original's for that reason, but it's a convention, not a lock.
- **Two payment ledgers now coexist.** Payments can allocate to an order (the punch flow) or to an invoice (accounting). Both are valid and neither is wrong, but a company's "Billed" figure on the 360 view still comes from its orders while its invoices settle separately — so the two can disagree until an order is actually invoiced. Closing that means invoicing from an order, which is the next slice.
- **Still to do for Zoho-Books parity**, in rough priority: invoicing directly from an order; emailing a document to the customer (Zoho's toolbar has Send and Share; there is now a mail transport — `src/lib/marketing/providers` — so this is wiring rather than infrastructure); GSTR-1 / GSTR-3B / HSN-summary reports; tax-inclusive rates (rates are exclusive today) and a document-level discount on top of the per-line one; multiple invoice templates; recurring invoices; vendor bills settling the same way invoices now do (payables mirroring receivables); refunding an unapplied credit note rather than only applying it.
- **A split view's list pane is one page deep.** It shows the rows from the current page of results, not an infinite scroll, and the paging controls only appear on the full table. Opening a record from page 2 works; scrolling past the 25th row inside the pane doesn't load the 26th. Switching to the table, paging, and switching back is the way through — worth revisiting if people start living in the split view.
- **Bulk selection is table-only.** The narrow pane has no checkboxes, so bulk actions mean switching to the table. That's deliberate — a third-width row has no room for one — but it does mean the two layouts aren't equivalent.

- **Never run `next build` while `next dev` is live.** Both default to `.next`, so a verification build overwrites the chunks the dev server is serving and the browser gets a stale mix — which presents as "my change didn't apply" even though the source is correct. Use `npm run build:check`, which builds into `.next-build` via `scripts/build-check.mjs` (a script rather than an inline env var, because npm runs scripts through cmd.exe on Windows). If the dev server has already been poisoned, stop it, delete `.next`, and restart.

- **Expenses and `OrderExpense` are two different ledgers.** The Expenses module covers what people and the business spend (travel, subscriptions, office costs) with an approval chain. `OrderExpense` — commission, freight, installation — is cost-of-sale attached to one order and belongs to that order's margin, so it has no claimant, no approval and no reimbursement. They're deliberately not merged, but that means "everything the company spent" is currently two reports rather than one. A combined view, or a source filter on the Expenses list, is the natural follow-up.
- **No approval thresholds or multi-step approval.** Every claim goes to exactly one person regardless of amount — there's no "over ₹10,000 also needs a director" rule, and no delegation while a manager is away beyond the `expenses.approve` override.
- **Visits have no calendar view or route planning**, and nothing checks that a check-in happened anywhere near the address. Mileage is typed, not measured.
- **Expense policy isn't enforced** — no per-category caps, no duplicate-receipt detection, no per-diem rules. An approver sees the claim and decides.

- **Trade documents don't talk to orders or payments yet.** The company 360 view now shows documents and payments side by side, but they're still two separate ledgers: `Payment` allocates against `CompanyProduct` (the order), not against a `TradeDocument`, so the Billed figure on a company comes from its orders while its invoices are counted separately. An invoice's `PARTIALLY_PAID`/`PAID` status still has to be set by hand, and issuing an invoice doesn't mark the order billed. This is the single biggest follow-up.
- **The NIC provider has never run against the real portal.** Its shape follows the published API (auth at `/eivital/v1.04/auth`, generate at `/eicore/v1.03/Invoice`, cancel at `/eicore/v1.03/Cancel`, ~6h token cached for 5), and every failure path returns a readable message instead of throwing — but everything verified in this pass went through the `mock` provider. Sandbox credentials are needed before it can be called working.
- **No e-way bill.** The IRP also issues e-way bills for goods movement above the threshold; only the IRN/QR half is built.
- **A credit note can exceed the invoice it reduces.** `convertTradeDocument` copies the invoice's lines verbatim and the amounts are then editable, but nothing checks the total against the original, or against credit notes already raised against it.
- **Conversion copies totals, not just lines.** A converted draft carries the source's stored tax figures until it's saved again; if the party's GSTIN or location changed in between, the draft shows stale tax until someone opens and saves it. Issuing doesn't recompute.
- **`einvoiceMinValue` is a flat threshold**, not the real turnover-based exemption rules — it's a convenience for skipping small invoices, not a compliance feature.
- **No bulk actions or CSV export on document lists**, and no date-range filter — only status, search and pagination.
- **Bulk selection covers one page at a time.** There's no "select all 158 matching records across every page" — by design, since the client only has the rows it was sent, but it means a bulk edit over a large filtered set takes a pass per page. A filter-scoped bulk action (act on everything the current filter matches) would be the natural follow-up.

- Performance tracking's "records created/edited" only covers Company, Contact, Lead, Order, Ticket, Task, and Payment(create) — deliberately the record types staff actually work with day to day, not literally every mutation in the app. Not audited: locations, industries, departments, module/permission/security settings, lead requirements, payment allocation/un-allocation, contact/company deletion, vendor status/code changes, and CSV import/export. A user who spends most of their time on an un-audited action type (e.g. managing locations) will show artificially low "records edited" — worth widening if that turns out to matter in practice.
- "Time spent on the CRM" is a heartbeat-based approximation (30s pings, only credited while a tab is open and visible, capped so a sleeping laptop doesn't rack up hours) — not a precise timesheet, and it can't distinguish "actively working" from "tab open, reading, not clicking." Two tabs open at once could double-count overlapping time (each tab heartbeats independently). No week/month rollup view yet — the date-range picker works, but there's no default "this week" / "this month" preset shortcut the way task/renewal filters have.
- "Leads won" is approximated from `Lead.updatedAt` falling in the selected range, since there's no dedicated "won at" timestamp on `Lead` — editing any other field on an already-won lead would also shift it out of a date-scoped count (or into one), which is a real (if narrow) source of inaccuracy. The exact WON transition timestamp does exist in each lead's `Activity` log (`STAGE_CHANGE` entries logged by `updateLeadStatus`) but querying that per-user across all leads wasn't built out for this pass.
- No export (CSV) from `/performance` — everything Leads/Items export already has, this page doesn't yet. No per-user drill-down either (e.g. "show me exactly which records Arjun created this week") — the page is rollup counts only, not a browsable activity feed, even though the underlying `AuditLog` rows would support one.
- Order Punching didn't get to the "sales person performance revenue-wise" half of the ask — `/performance` still only reports records-created/edited and ticket metrics, not fulfilled-order revenue or margin per salesperson. The data to build it now exists (`CompanyProduct.orderStatus`/`unitPrice`/`purchasePrice`/`addedByUserId`), it just wasn't wired into `getUserPerformance()` in this pass.
- No stock/inventory consumption on order fulfillment — a `GOOD`-type item's `stockQuantity` isn't decremented when an order reaches `FULFILLED`, unlike the direct stock-movement flow the Items module already has for manual receipts/sales. An order for a physical good currently has no effect on inventory levels.
- `Proposal` still has no line items (Phase 3, unbuilt) — the order-punch form's "linked proposal" picker only lets you *reference* an existing proposal by its lead/status, it can't pull in what was actually proposed (products, quantities, pricing) to pre-fill the order.
- No email/in-app digest for accounts or purchasing when a new order needs their attention beyond the one-time watcher/status-change notifications already wired up — there's no "N orders awaiting your approval" nudge the way, say, an overdue-ticket SLA badge nudges support.
- Rejected and cancelled orders stay visible in Products & Subscriptions indefinitely with no way to distinguish "this never happened" from "this is a real order" at a glance beyond the status badge — no archive/hide affordance for a company with a long history of abandoned orders.

- "Awaiting Order" is computed from `CompanyProduct` existence, not stored — correct and always live, but it means there's still no code path that ever moves a company's `stage` *back down* from `CUSTOMER` (e.g. if its only order is deleted, or a WON lead is reopened) — it just starts showing "Awaiting Order" again once it has no orders, which happens to be the right display outcome here, but the underlying `stage` field can still drift from reality in other ways no UI surfaces (had to fix one such drift by hand with a script during this change's own verification).
- The Companies (raw pool) vs. Customer split only implements the "has purchased something" half of the request — the request also named two other graduation signals ("until we have sent them a proposal, or we have verified contact information of the concerned person"), but neither is tracked anywhere yet: there's no "proposal sent" flag independent of the `Proposal` entity's own status (and `Proposal` line items themselves are still Phase 3, unbuilt), and no "contact verified" flag on `Contact` at all. Every company without an order currently lands in the same undifferentiated Companies pool regardless of how far profiling/qualification has actually progressed — Prospect/Lead `stage` and a lead's own status are the closest existing proxies, but neither was wired into this specific split. Worth a dedicated follow-up if the raw pool needs its own sub-stages.

- Applying a department dashboard preset copies its widget list into the user's own `dashboardWidgets` at that moment — it isn't a live link. If an admin edits a department's preset afterward, everyone who already applied the old version keeps it until they explicitly re-apply. There's also no "this is currently applied from the Sales preset" indicator once applied — it just looks like a manual customization. No drag-to-reorder or widget sizing, only show/hide; every user sees the same fixed card order and layout.

- Notifications have no real email delivery yet (`sendEmailNotification` is a logging stub, see Delivered) and no per-user preferences (mute a type, digest instead of instant, etc.) — everyone gets every notification type that applies to them, in-app only. The bell polls every 45 seconds rather than pushing in real time (no websocket/SSE infra in this app). System-generated alerts (task overdue, ticket SLA breach, renewal expiring) are reconciled lazily on next fetch rather than on a schedule, since there's no background job runner — an alert can lag up to however long it's been since that user last opened the bell or visited the dashboard. Notifications also have no delete/archive, only mark-read, and there's no notifications history page — the bell only shows the most recent 20.
- Tasks have no recurrence, subtasks, priority field, or reminders-before-due-date (just a due date and a done flag) — kept deliberately minimal since none of that was asked for. A task can link to at most one of Company/Lead/Ticket (not several), and there's no bulk actions (mark several done, reassign several at once) on `/tasks`.
- `Company.relationshipType` (Client/Vendor/OEM/Distributor/Partner/Other) now has a dedicated Vendors workspace with its own onboarding lifecycle (`VendorStatus`), the shared company detail page hides the sales-pipeline tabs/stats for non-CLIENT companies, and every customer order (`CompanyProduct`) now records which vendor it was purchased from with that vendor's payment terms shown inline (see Delivered) — but there's still no real *purchasing* workflow behind that link: no vendor-side payments-we-owe ledger mirroring the client-side `Payment`/`PaymentAllocation` system (so there's no way to record that Wroffy actually paid the vendor for an order, or track an AP balance), no "products this vendor typically supplies" default on the Item catalog (`Item.vendor` is still free text, not linked to `vendorId` — the order-level vendor picker has to be set by hand every time, even for a SKU that's always sourced from the same distributor), and no purchase-order document/number of our own to the vendor (only the existing `poNumber` field, which is actually the *customer's* PO/invoice reference, not ours to them). The `/contacts` Library page is read-only/filter-only by design — there's no add/edit/delete from that page itself, only a link back to the contact's own company page where the existing edit/delete UI lives.
- No automated test suite yet — only Zod validation coverage on inputs. Add unit tests around `normalizeCompanyName`/uniqueness and integration tests around the lead status transitions before this goes to production use.
- Role-based access control now has a real, extensible mechanism (`PERMISSION_REGISTRY` + `RolePermission`, see Delivered), a user-aware layer on top of it (`hasEffectivePermission`/`getDownlineRoles`, inheriting a manager's downline permissions via `User.managerId`), but it's only wired up for product/requirement edit/delete, payment record/delete, and ticket create/delete so far. `canManageLeads`/`canSourceCompanies` in `src/lib/auth.ts` are still defined but unenforced, and most other actions (company/lead create-update-delete, contact management, CSV import/export, assignment) have no permission check yet — any authenticated user can still do those. Register more `PERMISSION_REGISTRY` entries and gate those actions before onboarding non-admin staff.
- Microsoft SSO's actual OAuth round-trip was never exercised live this session — it needs a real Azure AD (Entra ID) app registration, which only the account owner can create in their own Microsoft admin portal, and none was available. The provider wiring, the `signIn` callback's unknown-email rejection, and the enforcement toggles were verified by code review and by the Security form's own validation, not by an actual Microsoft sign-in.
- There's no way to *delete* a user from the UI, only deactivate (`setUserActive`) — matches how companies also have no delete UI, but is a real limitation for e.g. removing a mistakenly-created test account (had to be done with a one-off script this session). Password-reset delivery still has no email path — the transport now exists (`src/lib/marketing/providers`, with M365 SMTP suitable for transactional mail) but nothing calls it for password resets yet, so an admin still hands off the value themselves, shown once in the dialog.
- No backup/recovery codes for two-factor — if someone loses their authenticator device, the only recovery path is an admin using "Reset 2FA" on their account (which then requires them to re-enroll). `otplib` is pinned to the deprecated v12 API (the actively-maintained v13 rewired around composable crypto/base32 plugins and would need real testing to get right) — functional and still the most widely-used TOTP implementation in the Node ecosystem, but worth revisiting in a future pass. The `SecuritySettings` row also has no `updatedByUserId` audit field, same gap already noted for `SystemModule`.
- There's no UI to *create* a new user (only Settings → Team to assign an existing user's role/department/manager) — users still only come into being via `prisma/seed.ts`. Needed before this can onboard real staff without a direct DB/script step. Departments also can't be deleted while any user is still assigned to one (by design, to avoid silently orphaning the assignment) but there's no bulk-reassign helper for that case yet.
- Ticket SLA windows (`SLA_HOURS` in `src/lib/tickets.ts`) are hardcoded per priority, not configurable by an admin — no Settings screen for SLA policy yet, and no escalation/notification when a ticket goes overdue (it just shows a red badge if someone looks). Ticket title/description aren't editable after creation (only status/priority/assignee are) — fixing a typo in either means deleting and recreating the ticket. No CSV export/import for tickets (Leads and Items both have export, Items has import) and no pagination on `/tickets` (same gap as company/lead/item lists). Ticket→Lead/Proposal linkage doesn't exist — a support issue that turns into a sales opportunity has to be logged as a separate, unlinked lead.
- GST is calculated as a single combined amount from each item's `taxRatePercent` — there's no CGST/SGST-vs-IGST split (that needs Wroffy's own registered state to compare against the order's `CompanyLocation.state`, which now exists as data but isn't used for a split yet since Wroffy's own "home state" still isn't captured anywhere), and `CompanyLocation.gstTreatment` is captured for compliance/record-keeping but doesn't yet change how tax is calculated (e.g. SEZ/Overseas would typically be zero-rated in a real invoice — not implemented). There's also no real `Order`/`Invoice` entity — a `CompanyProduct` row doubles as "the order," which is fine for the current one-line-item-per-order model but won't hold up if a single order ever needs multiple line items.
- The consolidated `/renewals` and `/payments` pages don't show which location an order belongs to yet — only the company's own order table does. Low-effort to add (the data's already on the row) if a renewal/accounts manager working from those pages ends up needing it too.
- The Allocate dialog applies a payment's unallocated remainder to one order per submission — splitting across several orders means repeating the action, there's no "split N ways at once" form. No suggested/auto allocation either (e.g. oldest-order-first, or auto-filling the amount to exactly clear an order's balance) — the accountant always types the amount by hand. A company's standing unallocated credit isn't surfaced anywhere on the company page itself (only on `/payments`'s Payments-received table) — worth adding to the company Details/Products tab if accountants end up needing it there too.
- No pagination on company/lead lists — fine at low volume, will need it once the profile team's LinkedIn sourcing produces a large company list.
- Proposal line items (products, pricing) are out of scope until Phase 3 — the `Proposal` entity currently only tracks status/dates/notes.
- Contact edit/delete/one-click actions aren't permission-gated (unlike products/payments) — any authenticated user can edit or delete any contact. No country-code inference for the WhatsApp link either — it just strips non-digits from whatever was typed in the phone field.
- Bulk assignment has no notification to the assignee; they'll only see it by opening their filtered company list. Consider an in-app or email nudge once notification infra exists.
- Tags are free-form (`String[]`), not a managed taxonomy — fine for now, but duplicate near-identical tags (e.g. "Hot Lead" vs "hot lead") won't be merged automatically.
- `SystemModule` tracks `updatedAt` but not who flipped a toggle — add a `changedByUserId` if module changes ever need an audit trail.
- Item `vendor` is free text, not a managed vendor list — fine at this scale, revisit if vendor-specific reporting (e.g. "all Microsoft SKUs") becomes a real need beyond filtering by name.
- No item list pagination yet — matters once the catalog grows past what fits on one page.
- `LeadRequirement` quantity/notes can't be edited in place — only add or remove a line and re-add it with the right quantity.
- Industries can be added and renamed from Settings but not deleted — wasn't asked for, and deleting one referenced by companies would need a decision (reassign vs. block) that hasn't been made. `Category` on `Company` is still free text; only Industry was converted to a managed picklist.

- Leads have CSV export but not import (Items has both) — wasn't asked for here; would need the same kind of upsert-key decision Items made around SKU, but leads don't have a natural unique key. Companies still have neither.
- The kanban board's drag-and-drop has no keyboard-accessible equivalent — dragging is the only way to change status from the board. The status dropdown on a lead's own detail page (`LeadStatusControl`) still works fully via keyboard/screen reader, so it's not a dead end, just not reachable from the board view itself.
